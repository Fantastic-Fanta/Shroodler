Shroodler · Strategic Roadmap

Agentic Bug Bounty Suite

A sequenced plan to build Shroodler from a capable personal research tool into the primary loop for running a bug bounty engagement — where an agent finds, confirms, and reports, and you direct the work. Pure CLI and MCP. No UI, no dashboard, no web layer — ever.

Document date 2026-09-08
Horizon ~9 months
Phases 5 (0–4)
Current branch main (unstaged)

Honest state snapshot

Architecture is right. Two-session authz-diff, nonsense-id control on peer-write, guardrails, MCP server — the core abstractions are well-designed and not easily matched.

Most modules are brand new. The roadmap audit ran yesterday. peer-write, CSRF harvest, JS API surface, and chain findings have never been exercised on a real engagement under pressure.

Auth is the #1 reliability gap. Mid-crawl re-auth runs once on 401. OAuth/PKCE, Castle.io anti-fraud tokens, and MFA breaks lose the entire run with no recoverable signal.

No engagement memory. Every scan is independent. An agent can't ask "what endpoints haven't I tested on this program?" or "what object IDs did I find last week?"

MCP outputs are agent-hostile. Tools return raw JSON. An agent driving a loop needs compact, decision-oriented outputs — not 400-line crawl blobs to reason over.

The ingest pattern is solid. HAR → crawl JSON → authz-diff → peer-write is a real pipeline. The proxy-and-record workflow is already the correct fallback for WAF-protected targets.

PHASE 0

Foundation

Now → 6 weeks

Outcome: The code that already exists is reliable enough to trust on a real engagement. Auth doesn't break silently. The MCP surface is usable by an agent without drowning it in raw JSON. No new features until this gate is clear.

Prerequisite: Everything downstream depends on this. Adding Phase 1 engagement memory to an unreliable crawler just makes the wrong state persistent.
Auth hardening Blocker

Extend --login-recipe to handle OAuth callback + PKCE. Retry re-auth up to N times (configurable), not just once. On terminal failure, surface "session died at request N" with the last good URL — never silently produce garbage results. Add support for anti-fraud token injection hooks (Castle.io, DataDome) that require a JS-executing browser step.

--login-recipe · --reauth-max-retries · --session-died hook
MCP output compression P1

Every MCP tool that returns findings should have a --summary mode emitting compact, decision-oriented output: "3 IDOR leads — 2 need confirmation, 1 confirmed. Curl repros follow." Raw JSON stays available but must not be the default. An agent reasoning over 400-line blobs is an agent wasting tokens on formatting.

check_idor · peer_write · authz_diff → summary mode
Test coverage for new modules P1

peer-write, CSRF harvest, JS API surface, chain findings, and stored XSS are all untracked or just-landed. Each needs unit tests before they can be trusted. Integration tests against the existing target-apps submodule are the right harness. Don't add more features until these have test coverage.

packages/crawler-py/tests/unit/
FP calibration pass P1

Run peer-write, CSRF harvest, and JS API surface against 3+ real programs from your existing engagements. Log every false positive. A confidence-grade of probable that fires on every second endpoint isn't a signal — it's alert fatigue. Calibrate thresholds before filing bugs based on these checks.

confidence.py thresholds · known-benign list
Commit surface reduction

The working tree has ~30 modified files and 10+ untracked modules. Commit what works, cut what doesn't, and get to a clean main. A chaotic working tree is a signal that the codebase is outrunning comprehension — the right response is to stop and consolidate, not ship the next feature.

WAF-blocked-session handling

When WAF/bot-detection blocks the headless crawler, emit a structured waf-blocking-active-scan finding with a clear "switch to proxy-and-record workflow" recommendation and the exact CLI sequence. The current behavior silently produces a mostly-empty crawl JSON with no explanation.

waf-blocking-active-scan finding · recovery suggestion
PHASE 1

Engagement Memory

6 → 12 weeks

Outcome: Shroodler knows what it's already done on a program. An agent can ask "what endpoints haven't been tested yet?" and get a real answer. Scans accumulate, not restart from zero.

shroodler program init P1

Per-program state store: crawl JSON history, confirmed findings, discovered object IDs, session cookie snapshots, scan timestamps. Keyed by program slug (e.g. etoro-bugcrowd). Lives in ~/.shroodler/programs/. This is the foundation the agent loop reads from — without it, every session is amnesia.

shroodler program init etoro-bugcrowd
Endpoint coverage tracking P1

Track which endpoints have been: crawled, authz-diffed, peer-write tested, payload-tested. On each new scan, emit a coverage delta: "12 endpoints discovered since last run — 4 not yet authz-tested." MCP tool coverage_gaps returns this as a prioritized queue for the agent.

MCP: coverage_gaps · shroodler program status
Object ID persistence

Accumulate discovered object IDs (transaction IDs, account IDs, resource UUIDs) across scans per program. The peer-write playbook can pull from this store instead of requiring manual extraction each session. Cross-session ID correlation is where IDOR bugs live — if account #1's IDs from week 1 are still accessible in week 4, that's the finding.

program.object_ids · peer-write --from-program
Cross-scan finding dedup

Findings with the same id+url key across scans should surface as "persisted" rather than re-discovered. A finding that's been probable for 3 scans with no fix is more credible than one from a single scan. Surface a "persistence score" alongside confidence.

history · trend --persist-signal
MCP: program_state tool

A single MCP tool the agent calls at the start of any session to load engagement context: known endpoints, object IDs, unconfirmed leads, last scan timestamp, gaps. Returns a compact briefing, not raw JSON. This is the agent's "orient" step before deciding what to test next.

MCP: program_state · start_session
Session cookie lifecycle

Store session snapshots with their capture timestamp and expected expiry. Warn before running an authz-diff with a cookie that's likely expired. Auto-suggest a session refresh via session-export --cdp when the stored state is stale. Avoids running a whole peer-write pass on an expired session and getting 401s everywhere.

program.sessions · --cookie-max-age
PHASE 2

The Agent Loop

12 → 20 weeks

Outcome: An agent can drive a full engagement cycle — triage → crawl → authz-diff → confirm IDOR leads → draft submission — with you reviewing and approving at each gate, not doing the mechanical work. This is Shroodler's differentiator; nothing else closes this loop.

Depends on: Phase 0 (reliable auth + compact MCP outputs) and Phase 1 (engagement memory). The agent loop is useless if it can't tell what it's already done.
Agent-driven IDOR confirmation P1

The existing IDOR probe explicitly documents "manual confirmation required." Close that gap: spin up a second test-account session, replay the candidate URL, compare ownership/PII fields (user ID, email, account-specific data) between sessions to confirm or drop the lead. MCP check_idor already has the right interface — this wires the second session to it systematically.

check_idor --peer-session · --require-identity-confirmation
Orchestration entrypoint P1

A single MCP tool that sequences a full engagement pass: load program state → triage new hosts → crawl → authz-diff → peer-write against stored IDs → surface confirmed leads → generate draft submission. Each step has an explicit approval gate before the next active step. The agent proposes; you approve. Never fully autonomous on writes.

MCP: run_engagement · --gate-on-active
shroodler ask — refinement

The ask interface already exists. Make it useful: it should answer "what's new since Tuesday?", "which findings are confirmed and unfiled?", "show me the authz-diff results for /api/orders/." Structured queries over the engagement state, not freeform LLM chat over raw JSON.

shroodler ask "confirmed findings not yet filed"
Adaptive payload — feedback loop

payload --adaptive already exists as a single mutation per pack miss. Wire it to the agent loop: after a 403 on a payload-shaped request, the agent proposes a WAF-evasion variant, you approve, it fires once. Log the outcome. Never more than one extra request per approval. The audit log from guardrails already covers this — just surface it to the agent.

payload --adaptive · MCP: propose_payload_variant
Submission draft generator

Given a confirmed finding (with curl repro, ownership proof, and confidence chain), generate a draft Bugcrowd/HackerOne submission: title, severity justification, impact, steps to reproduce, supporting evidence. Plaintext, not an upload. You edit and file; the tool does the mechanical structure.

shroodler report --format bugcrowd-draft
Pre-submission calibration

Before you submit: a checklist tool that asks the questions the bug-bounty-playbook learned the hard way — "Is the impact section doing hypothetical chaining work? Is the finding excluded by the program's scope? Does the severity match the program's reward scale?" Catches the bcrypt-salt class of near-miss before it burns your signal score.

shroodler calibrate --finding findings.json
PHASE 3

Discovery Pipeline

20 → 28 weeks

Outcome: Triage is the orchestrated entry point for every engagement, not a standalone tool. The pipeline from "I have a program scope" to "here are the hosts worth crawling and here are the endpoints worth testing" is fast, safe, and reproducible.

Triage as workflow entry P1

shroodler triage exists but is a standalone command. Make it the canonical first step: pipe its output directly into crawl --hosts-from, store the classification results in program state, and have the agent begin every session by checking whether the triage is stale. The wien.gv.at incident (unbounded fan-out tripping a WAF) is the anti-pattern the tool exists to prevent.

triage --save-to-program · crawl --hosts-from triage.json
Auth-stack probe library P1

Extend auth-stack fingerprinting beyond next-auth/Keycloak/Auth0. Each detected stack should automatically trigger its known-pattern probes: Supabase (JWT secret bruteforce resistance check), Firebase (rules misconfiguration), Cognito (user enumeration via error messages), generic OAuth (state param CSRF, implicit flow). Start with the stacks you actually encounter on your programs.

extractors/auth_stack.py · --auth-probes
GraphQL discovery depth

When introspection is blocked, the Clairvoyance integration already feeds field names. Extend: auto-detect common GQL frameworks (Apollo, Hasura, Relay) by response signatures and apply known framework-specific checks (Hasura's X-Hasura-Admin-Secret, Apollo's persisted queries endpoint). Maintain a small built-in wordlist of high-value field names (password, token, ssn, adminOverride) as a default.

--gql-wordlist built-in · gql-framework fingerprint
JS route → authz-diff pipeline

shroodler js-routes extracts URL templates from bundles. Complete the pipeline: extracted templates → parameterize with stored object IDs → feed into authz-diff as additional test targets. Today these are separate manual steps. The agent should be able to run "extract routes from bundle, test each parameterized URL against the lower-priv session" as one orchestrated pass.

js-routes | authz-diff --template-urls
OAuth / OIDC probe expansion

Beyond the existing state-param and implicit-flow checks: PKCE downgrade (does the server accept plain when the client sends S256?), token leakage via Referer on redirect, prompt=none silent auth bypass, cross-origin token endpoint probing. Each probe is a discrete finding with a clear description of the conditions that trigger it.

extractors/oauth.py · --oauth-deep
Program scope management

Store the program's in-scope / out-of-scope specification in program state. Before any active test, check the target URL against the scope. Emit a clear warning (not a block, but a warning) when a crawl or payload test is about to hit an out-of-scope host — the safe-harbor risk of testing out-of-scope is real and was felt on the eToro engagement.

program set-scope · --scope-check-strict
PHASE 4

Submission Quality

28 → 36 weeks

Outcome: Findings that come out of Shroodler are submission-ready. Minimal repros are tight. Severity is calibrated. Duplicate-check against known program history is automatic. The gap between "Shroodler found this" and "I submitted this" collapses.

Minimal repro automation P1

Binary-search the payload pack down to the shortest variant that still triggers the same confidence-level result. Today Shroodler reports whichever payload hit first — that's rarely the cleanest repro. A tight, minimal curl command is a significantly better bug report than a payload-dump, and it demonstrates the researcher understood the vulnerability rather than running a scanner.

payload --minimal-repro · minimal_repro: true
Duplicate detection P1

Before finalizing a submission: check the finding against your own previously-filed findings (by endpoint pattern + finding type) and, where available, check against known program disclosures. Filing a duplicate that you yourself found 3 months ago is avoidable. The program state store from Phase 1 makes this possible; this is the output layer for it.

shroodler calibrate --check-duplicates
CVSS auto-scoring

Given a finding's type, confidence, and the conditions under which it fires, emit a draft CVSS 3.1 vector with a plain-English explanation of each axis choice. Not a replacement for judgment — a starting point that prevents the "I said Critical, triager said Low, now I'm appealing" cycle. Especially useful for the cost-of-attack axis the codebase already partially computes.

report --cvss · cost_of_attack.py
Platform-specific report formats

Bugcrowd and HackerOne have different submission templates, severity scales, and required evidence fields. Shroodler should know the difference. A --format bugcrowd report maps severity to Bugcrowd's P1-P5 scale and includes the fields their form expects; --format hackerone does the same for HackerOne's structure. Less time reformatting, more time finding.

report --format bugcrowd · --format hackerone
Evidence packaging

A confirmed finding should produce a self-contained evidence bundle: the curl repro, the request/response pair, the ownership-proof comparison (for IDOR), and the confidence chain. One file, attached to the submission. Today this is assembled manually from scattered JSON output. Bundle it automatically at confirmation time.

shroodler report --bundle-evidence · evidence.zip
Regression test on close

When a program closes a finding as fixed, shroodler gen-regression-test already exists. Integrate it into the ticket-sync workflow: when a GitHub issue is closed as fixed, auto-generate the regression test and add it to the program's test suite. The finding's fix comes with a guard by default, not as an afterthought.

ticket sync --on-close gen-regression-test

Considered for Phase 4, intentionally deferred

  • AI-written submission narratives — adds AI noise to a document where your credibility is the point
  • Automatic submission filing — program platforms require human attestation; keep the human in the loop here
  • CVSS arbitration / triager negotiation tooling — this is a relationship problem, not a tool problem

Hard DEFER — do not build these

These are attractive because they look like scope. They are not scope. Each one is a multi-year distraction from a better-executed core.

WebSocket / gRPC / SOAP / protobuf
Multi-year protocol catch-up. ZAP already has all of it. The right answer is ingest-har for WS traffic, not a WS scanner.
Nuclei-scale template library
Community scale is not replicable solo. nuclei-ingest is already the right answer — consume their templates, don't compete on volume.
Multi-role authz-diff (>2 sessions)
Two-session diff covers 95% of real bug bounty authorization bugs. Three-role complexity is for internal pentest tooling, not a single-researcher workflow.
Free-form LLM payload generation
--adaptive with guardrails is the safe version and already exists. Unconstrained live generation against a production target is not controllable enough to be defensible.
Running Slither / Nuclei as subprocesses
The ingest pattern is correct. Vendoring or shelling out to external analyzers creates a maintenance dependency and version-compatibility burden with no upside.
Any UI — GUI, web dashboard, TUI
CLI is the interface. MCP is the agent interface. Every hour spent on a UI is an hour not spent on making the crawler and authz-diff more reliable. The audience is one researcher who is fluent in a terminal.
